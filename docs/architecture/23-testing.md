# Testing strategy

## 1. Starting position

The current codebase has ~1,464 lines of API unit tests concentrated on pure
logic in `core/`, seven manual `.mjs` E2E scripts, solid pytest coverage on the
Python agent — and **zero frontend tests across 11,525 lines of React**.

The new UI is roughly 10× larger and adds drag-and-drop, virtualization and
realtime: the three hardest things to verify by eye. That gap does not survive
contact with Phase 1.

## 2. The pyramid, weighted for this system

| Level | Tool | Count | What it covers |
|---|---|---|---|
| Unit | Vitest | ~2,000 | Pure logic: filter AST, LexoRank, rank arithmetic, permission matrix, date bucketing, reducers |
| **Tenancy (generated)** | Vitest | 1 suite, all functions | The poison-row suite — see §3 |
| Repository | Vitest + testcontainers | ~300 | Real Postgres. Scoping, constraints, transactions, cascade behaviour |
| Service | Vitest | ~400 | Business invariants with mocked repositories |
| API contract | Vitest + `app.inject` | ~300 | Every route: auth, validation, status codes, envelope |
| Component | RTL | ~200 | Design-system primitives, complex components |
| Visual | Storybook + Chromatic | Every primitive | Light and dark |
| E2E | Playwright | 12–15 journeys | The paths that must never break |
| Performance | Playwright + fixture | 6 assertions | The budgets in [21-performance.md](21-performance.md) |
| Accessibility | axe-core | Every route | WCAG 2.1 AA |
| Load | k6 | 5 scenarios | Pre-launch and quarterly |

## 3. The poison-row suite — the one that matters

Described in [03-tenancy.md](03-tenancy.md). Restated here because it is the
single most important test in the system:

```
1. Seed workspace A and workspace B
2. Insert one row into EVERY tenant table under workspace B
3. Enumerate every exported repository function by reflection
4. Invoke each as a workspace-A principal, with fuzzed arguments
5. Assert: zero B rows returned, mutated, or deleted
```

Generated by reflection, so a function added next year is covered without anyone
remembering.

**Phase 0 exit requires proving it works:** delete one `workspace_id` predicate
and confirm CI goes red. An untested guard is not a guard — it is a comment.

## 4. Test data

One seeded fixture, used by performance tests, E2E and manual QA:

```
1 workspace · 200 users · 50 projects
500,000 issues · 2,000 in the largest board column
100,000 comments · 1,000 docs · 50,000 time entries
```

Built by a deterministic seeder with a fixed PRNG seed, so failures reproduce.
Committed as code, not as a dump.

**Performance assertions run against this fixture, never an empty database.**

## 5. E2E journeys

The 12–15 paths that must never break. Established in Phase 0 with the first five:

1. Sign in → land in workspace
2. Create project → create issue → appears on board
3. Drag issue between columns → persists across reload
4. Comment with @mention → recipient's notification bell updates
5. Search finds the issue just created
6. Invite member → accept → both see the workspace
7. Two browsers: change in one appears in the other without refresh
8. Kill the WebSocket → client falls back to polling → stays correct
9. Bulk edit 50 issues → partial success reported accurately
10. Sprint: plan → start → complete → report renders
11. Upload attachment → download it
12. Client-role user sees only shared projects, and no workspace-wide surface
13. Timer start → stop → appears on the timesheet
14. Export → job completes → download link works
15. Automation rule fires on the expected trigger

Journeys 7, 8 and 12 are the ones that catch architectural regressions.

## 6. Realtime and concurrency testing

The hardest category, and the one most likely to be skipped:

| Test | Method |
|---|---|
| Out-of-order event delivery | Synthetic event streams with shuffled versions; assert cache converges |
| Optimistic update + echo | Apply locally, deliver the echo, assert no duplicate and no revert |
| Version conflict | Two clients edit; assert 412 and a non-destructive conflict view |
| Rank under concurrency | **Property test: 10,000 random concurrent moves; assert unique total order preserved** |
| Reconnect replay | Disconnect, mutate, reconnect; assert missed events arrive exactly once |
| Permission revocation | Remove a member; assert their socket closes and further requests 404 |

## 7. CI gates

| Stage | Blocking | Runs on |
|---|---|---|
| typecheck, lint | ● | Every PR |
| unit + service | ● | Every PR |
| **tenancy suite** | ● | Every PR |
| repository (testcontainers) | ● | Every PR |
| API contract | ● | Every PR |
| component + visual | ● | Every PR |
| bundle budget | ● | Every PR |
| E2E | ● | Every PR (parallel shards) |
| a11y | ● | Every PR |
| performance | ● | Nightly + release |
| migration forward/back | ● | Every PR touching migrations |
| load | | Pre-launch, quarterly |

Coverage floors: 80% on `packages/core` and `packages/db`, 60% on apps. Floors
are a ratchet — they may rise, never fall.

## 8. What we deliberately do not test

Stated so nobody adds them out of habit:

- Third-party library internals
- Generated code (OpenAPI, Drizzle types)
- Exact CSS values — visual regression covers appearance
- Trivial getters and pass-through mappers
- Supabase Auth itself — we test our integration, not their product

## 9. Manual QA

Automation does not replace judgement on:

- Visual polish and animation quality
- Keyboard flow end to end
- Screen-reader experience (NVDA and VoiceOver, quarterly)
- Whether a new feature actually feels fast

## 10. Risks

| Risk | Mitigation |
|---|---|
| Frontend testing is deferred "until the UI settles" | Playwright established in Phase 0 with 5 flows, before there is much UI to retrofit |
| Flaky E2E erodes trust in CI | Quarantine on second flake, fix within a week, no retries masking real failures |
| The tenancy suite is disabled to unblock a release | It is a required check; disabling it requires an admin override that pages the security owner |
| Test data drifts from production shape | The fixture is generated from the real schema; migrations run against it in CI |
| Performance tests run on an empty database and pass meaninglessly | Budgets asserted only against the large fixture |
