# 0002 — Repository-layer scope guard, not Postgres RLS

**Status:** Accepted · 2026-08-06

## Context

Every tenant table carries `workspace_id`. Roughly 200 repository functions will
query them. A single missing predicate is a cross-workspace data leak —
catastrophic and reputationally unrecoverable.

Postgres row-level security is the reflexive answer to this problem.

## Decision

Enforce isolation in the repository layer, with four independent mechanisms:

1. A branded, non-forgeable `RequestContext` produced only by the auth plugin
2. A `scoped()` builder every query passes through, with no "all workspaces"
   escape hatch
3. CI-enforced structural invariants (schema lint, index lint, ESLint ban on raw
   `db.*` outside repositories, AST check on the first parameter)
4. A **generated poison-row test suite** that invokes every repository function
   as a foreign principal and asserts zero rows cross

Mechanism 4 is the actual guarantee. The rest are ergonomics.

## Alternatives

**Postgres RLS.** Rejected for three reasons:

1. **The authorization logic is not row-simple.** Access is
   `capability × workspace membership × project membership × client-share ×
   archived state`. Expressing that as policies means writing the business rules
   twice — once in TypeScript where they are typed, tested and debuggable, once
   in PL/pgSQL where they are none of those. The two will drift, and the drift is
   a security bug.
2. **Pooling friction.** RLS needs `SET LOCAL app.workspace_id`. Against a
   transaction-mode pooler that is only safe inside an explicit transaction, so
   every read becomes one. In session mode a leaked `SET` is a cross-tenant bug
   with no stack trace.
3. **The existing pattern already solves the hard part.**
   `api/src/repositories/scope.ts` returns `sql\`false\`` for an empty scope —
   zero rows, never all rows. That fail-closed semantic is the defect class RLS
   is usually adopted to prevent, and it is already handled in testable code.

**Schema-per-tenant.** Rejected: thousands of workspaces means thousands of
schemas, migrations become an orchestration problem, and cross-workspace queries
(my-work, my-notifications) become unions over N schemas.

**Database-per-tenant.** Rejected for the same reasons, more so.

**Review discipline alone.** Rejected: does not scale to 200 functions maintained
over years by a changing team.

## Consequences

- Isolation depends on application code being correct, so the test suite is
  load-bearing rather than nice-to-have
- Anyone with direct database credentials bypasses all of it — so nobody gets
  them, and admin tooling goes through the same repositories
- New repository functions are covered automatically only because the suite is
  generated by reflection; a hand-written suite would rot

## Reversal

Revisit if either becomes true:

- **Untrusted clients need direct database access** (a PostgREST-style public
  data API). Then RLS is the only workable boundary.
- **A compliance regime requires isolation enforced below the application
  layer**, and an auditor will not accept a test suite as evidence.

Neither is on the roadmap. If the first arrives, RLS becomes an *additional*
layer, not a replacement — defence in depth, with the repository guard retained.
